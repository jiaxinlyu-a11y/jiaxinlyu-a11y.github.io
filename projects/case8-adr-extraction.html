Case study · Pharmacovigilance text mining · Python and an LLM API

Can an LLM find its own evidence, not just classify it?

Building on the medical-coding case, I asked an LLM to do the harder half of the job: read a patient's own unedited forum post and find the adverse-reaction mentions itself, then map each one to a standard SNOMED CT term. 89.0% of real mentions found (extraction F1 85.4%), 70.5% mapped to the exact right standard term — up from 64.4% after reading the actual mistakes and rewriting the prompt around them (+6.1 points).

01The task

CSIRO's CADEC dataset: 1,250 posts from patient forums about five arthritis/pain drugs, hand-annotated with every adverse-reaction (ADR) mention and its position in the raw text. The earlier case started one step downstream — already-clean terms, ready to classify. Here the text is real and messy: full sentences, typos, several reactions buried in one paragraph, nothing pre-cut. The model has to find the spans itself before it can map them.

1,250raw forum posts across 11 drugs, none pre-segmented
5,316hand-annotated ADR mentions to find and map
730distinct SNOMED CT standard terms actually present in the data

Standardised to SNOMED CT, not MedDRA. MedDRA's own term text is commercially licensed, so CADEC's MedDRA files carry codes with no names attached — the same restriction that shaped the earlier case. SNOMED CT is open, so its files carry both code and name, making it the only practical target. As before, the candidate list is only the 730 terms this dataset actually uses, never a full external dictionary.

02The pipeline

Three Python scripts.

ScriptWhat it does
prepare_dataBuild the ground-truth table: match each human-marked ADR span (by character position) to its SNOMED CT code and name, across all 1,250 posts
classifyThe core pipeline — for each raw post, one LLM call finds every ADR span itself and maps each to the closest of the 730 candidate terms, scored against the ground truth with a simple overlap rule
eval_strictRe-scores the same saved results under exact boundary matching instead of overlap — no extra API calls, just a stricter yardstick on the same data

Same model and setup as the earlier case: DeepSeek's deepseek-chat, low temperature (0.1), JSON output. A span counts as found if the model's guess overlaps the true span's position at all; among found spans, the mapping counts as correct only if the standard term matches exactly.

03Baseline: extraction works, mapping lags

First full run, all 1,250 posts, bare-list prompt (candidate terms, no hints).

89.4%of real ADR mentions found (4,753 of 5,316), unprompted — the new skill vs. the earlier case
64.4%of found spans mapped to the exact right standard term

The extraction half — the genuinely new skill over the earlier case — was strong from the first try. Mapping, the part that carries over from the earlier case, landed at roughly the same level it started at there too (83.9%, pre-fix) — worth reading the actual mistakes before touching the prompt.

04Reading the errors

1,690 spans were found but mapped wrong. Not all of those are real classifier mistakes: 165 had no standard term in the ground truth to begin with, and 14 were the model correctly declining with "NONE". The remaining 1,511 — a real wrong pick — were counted by which two terms kept getting swapped.

Over 89% of real mapping errors were near-synonym confusion, not random noise. SNOMED CT holds a formal medical term and a plain-English equivalent as two separate entries far more often than expected (amnesia/memory impairment, arthralgia/joint pain), and the model consistently reached for the more familiar-sounding sibling rather than the one the human annotators actually picked.

05The fix: let the data name its own confusions

Rather than a generic instruction ("prefer the more specific term"), which turned out to point the wrong way about as often as the right one, the top 16 highest-frequency confusion pairs were written into the prompt directly — a standing rule of thumb for exactly the pairs the data showed were being swapped, nothing invented.

VersionPromptMapping accuracyChange
v1Bare candidate list64.4%—
v2+ 16 explicit tie-break rules, mined from the actual confusion pairs70.5%+6.1 pts

Extraction recall (89.0%) and precision (82.0%) held steady, as expected — only the mapping half of the prompt changed. The gain held up across drugs individually, not just in the pooled total, which is what makes it a real fix rather than a fit to one subgroup.

06What this didn't fix

Two honest limits, surfaced by checking rather than assuming the headline numbers tell the whole story. First: LIPITOR alone is 877 of the 1,250 posts (84% of all ADR mentions), so the pooled result is mostly a measurement of LIPITOR — the other ten drugs' individual numbers are each based on too few posts (1–127) to trust on their own.

Second: re-scoring the same results under exact boundary matching, instead of "any overlap counts", drops extraction F1 from 84.3% to 61.6%. The model usually lands in the right place but doesn't always cut the span at exactly the same words a human would — close, not word-for-word. The overlap rule was the right call for this project's scope, but it was worth checking what a stricter yardstick would have said.

Bottom line. The new skill — finding evidence in raw text instead of being handed it — worked well from the first try. The skill that carried over from the earlier case — picking the right standard term — improved the same way it did there: by reading the real mistakes, not guessing at a fix, and letting the data name exactly which confusions to correct for.
