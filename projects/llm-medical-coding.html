Case study · Medical coding · Python and an LLM API

Can an LLM sort adverse events into their medical category?

I used an LLM as a zero-shot classifier to sort 242 adverse-event terms into their MedDRA System Organ Class: 83.9% accuracy with a bare-bones prompt, 86.8% after reading the actual mistakes and rewriting it (+2.9 points). This is a small, honest study of what prompt engineering can and cannot buy you on a coding task.

01The task

Reusing the adverse-event data from the CDISC pilot case: 1,191 adverse-event records, each with a verbatim term (AETERM, what was typed at the site) and its official classification into one of 23 MedDRA System Organ Classes (AEBODSYS). The task: given only a term, predict which of the 23 categories it belongs to.

242distinct verbatim terms, after removing duplicates across subjects
23candidate categories (System Organ Classes), shown in full on every call
1 to 292terms per category — badly imbalanced, which matters later

No licensed MedDRA dictionary was used. The categories and the correct answers both come from this public dataset's own coding, which is standard for a practice case like this.

02The pipeline

Five small Python scripts, each with one job, run in order from the command line.

ScriptWhat it does
prepare_dataBuild the clean inputs: 242 distinct terms with their true category, and the list of 23 category names
classifyFor each term, call the LLM with a system prompt listing the 23 categories; save its pick next to the true answer
evaluateScore any one results file: overall accuracy, accuracy per category, and a csv of every wrong case for manual review
classify_v2Same as classify, but the prompt now gives a one-line description of each category, not just its name
comparePut two results files side by side and export the before/after accuracy to Excel

The LLM is DeepSeek's deepseek-chat model, called through an OpenAI-compatible API, at low temperature (0.1) for a stable, repeatable pick. No fine-tuning: the whole task leans on the prompt alone, which is what makes it a fair place to test prompt engineering.

03Baseline: category names alone

The first prompt just listed the 23 category names and asked the model to pick one, copied exactly, for each term. No examples, no descriptions — the simplest version that could work.

83.9%overall accuracy, 203 of 242 terms correctly classified

Reasonable for a first pass with zero examples, but a few categories stood out as consistently weak: INVESTIGATIONS (57.9%), INFECTIONS AND INFESTATIONS (61.1%), and GENERAL DISORDERS AND ADMINISTRATION SITE CONDITIONS (73.5%, the single largest category at 34 terms) — too big and too wrong to blame on small samples alone. That is what made reading the actual mistakes worthwhile rather than guessing at fixes.

04Reading the errors

The evaluate script saves every wrong case — term, true category, predicted category — so the mistakes can be read rather than just counted. Two clear, repeating patterns turned up.

TermTrue categoryPredicted
BIOPSYInvestigationsSurgical and medical procedures
CYSTOSCOPYInvestigationsSurgical and medical procedures
HEART RATE INCREASEDInvestigationsCardiac disorders
CYSTITISInfections and infestationsRenal and urinary disorders
CERVICITISInfections and infestationsReproductive system and breast disorders
RHINITISInfections and infestationsRespiratory, thoracic and mediastinal disorders

Pattern 1: a diagnostic act gets read as a treatment, or as the organ it measures. A biopsy or a cystoscopy is a test, not surgery — the model routed it to SURGICAL AND MEDICAL PROCEDURES instead of INVESTIGATIONS. A rising or falling measurement (heart rate, body temperature) got filed under the organ it relates to, rather than recognised as a measurement itself.

Pattern 2: an infection named after the organ it affects gets filed under that organ. CYSTITIS, CERVICITIS and RHINITIS are all infections (the “-itis” ending), but the model saw “bladder”, “cervix” or “nose” and filed them under that organ's own disorder category instead of INFECTIONS AND INFESTATIONS.

A few other errors (LETHARGY, LISTLESS, SUDDEN DEATH) didn't fit either pattern — these looked more like genuinely ambiguous coding choices in the source data than something a better prompt could fix, and were left alone.

05The fix: one line of context per category

v2 adds a plain one-line description to every category in the prompt, not just its name — and for the three weakest categories, that description names the two error patterns above directly. INVESTIGATIONS now explicitly says it covers “a diagnostic test or measurement… not a treatment”; INFECTIONS AND INFESTATIONS now says organ-named infections (“-itis”) still belong there. Same idea everywhere, sharper wording where the model was actually getting confused.

VersionPromptAccuracyChange
v1Bare category names83.9%—
v2+ one-line description per category, sharpened for the categories that were actually wrong86.8%+2.9 pts

A genuine, if modest, gain — and one earned by reading the actual mistakes first, not by guessing at what might help.

06What prompt engineering couldn't fix

A ~3-point gain from one round of prompt work, not a leap to near-perfect accuracy — and that ceiling has two real causes, not one. Several categories have only one or two example terms in this dataset; with that few examples, a single right or wrong guess swings the category's accuracy by 50 to 100 points, and no prompt can fix what is really just too little data to judge. Separately, a handful of terms (LETHARGY, SUDDEN DEATH) look like the source data's own coding call could reasonably have gone either way — a model, or a person, could defend a different category without being wrong.

Bottom line. Error analysis beats guessing: reading the actual mismatches pointed at two specific, nameable confusions, and fixing those specifically worked better than a generic prompt improvement. But a classifier's ceiling is partly set by the data itself, not just the prompt — knowing which is which is part of the job.
