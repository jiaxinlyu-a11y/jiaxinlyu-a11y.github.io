Building a project-management system

I owned this internal system end to end. The hardest part was that most departments could not say what they needed, so I surveyed existing tools, worked out requirements from how each department works, designed the process, and delivered the system.

01The problems

There was no ready answer to “what should the system do?”, and four things had to be solved before any screen could be designed.

02Choosing a management approach

Popular systems look alike on screen. The real difference is how each one organises work, and what that costs to run.

03Requirements nobody stated

Only one department could say what it needed. For the others I asked about their business and worked the requirements out.

04One process per project type

Software and hardware projects deliver different things, and strict-standard projects have stricter acceptance, so a single workflow would have fitted none of them.

05Delivery and archiving

Software, hardware and trade projects each have to archive a different set of files, so I turned the required documents into a checklist for each type.

06Conclusion

I led the system from the first survey of existing tools to delivery. The tools differed in how they organise work and how much effort they take to run, not in their screens, so I based the flow on how the company really runs projects. I worked out the missing requirements from the departments’ own work, and gave each project type its own flow and file checklist. A second phase was left as a reserved interface for later upgrades.
